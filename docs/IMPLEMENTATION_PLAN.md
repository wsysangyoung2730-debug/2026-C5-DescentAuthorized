# 비UI 프로토타입 구현 계획

> 문서 상태: 과거 구현 계획 참고 자료
> 최신 구현 현황: [`CORE_IMPLEMENTATION_STATUS.md`](CORE_IMPLEMENTATION_STATUS.md)
> 마지막 분류: 2026-09-01

## 1. 목표

이 계획은 화면과 아트 연출을 제외하고 `하강 승인: 제0균열` 데모의 규칙을 실행 가능한 순수 Swift 게임 코어로 구현하는 것을 목표로 한다.

완료 시 다음 작업이 가능해야 한다.

- 정규화된 Pencil/손가락 획 데이터를 주문 문양으로 판정한다.
- 실제 선 길이에 따라 마나를 소비하고 말소 구역의 추가 소비를 반영한다.
- 한 턴 최대 2획 안에서 주문을 한 번 또는 연속으로 시전한다.
- 공격, 고정 방벽, 일반 방어막 관통과 절대 방어막 해제를 처리한다.
- 기록 관리자, 관측 잔류체, 관측 관리자의 패턴을 자동 진행한다.
- 10층부터 8층까지 주문 습득, 전투, 보상과 체크포인트 상태를 진행한다.
- 진행 상태를 기기 내부에 저장하고 복원한다.
- UI 없이 자동 테스트와 시뮬레이션으로 주요 규칙을 검증한다.

## 2. 제외 범위

- 실제 전투 화면과 카드 UI
- Apple Pencil 이벤트를 받는 UIKit/SwiftUI 입력 화면
- RealityKit 2.5D 무대와 카메라
- 캐릭터, 배경, 글로우와 피격 애니메이션
- 사운드와 햅틱 재생
- 실제 보상 선택 화면
- 실제 기기 화면 좌표를 정규화 좌표로 바꾸는 뷰 계층

UI 계층은 추후 코어가 제공하는 상태와 이벤트를 구독하고, 정규화된 획을 코어에 전달하는 역할만 맡는다.

## 3. 아키텍처 원칙

### 3.1 의존 방향

```text
UI / RealityKit
      ↓
Application Services
      ↓
Combat / Progression / Glyph Engines
      ↓
Domain Models and Content Catalogs
```

- 도메인과 엔진은 SwiftUI, UIKit, RealityKit을 import하지 않는다.
- 콘텐츠 수치와 문양 좌표는 카탈로그에 모으고 엔진에 직접 작성하지 않는다.
- 전투 엔진은 화면을 직접 변경하지 않고 상태와 이벤트를 반환한다.
- 저장 계층은 프로토콜 뒤에 두어 테스트에서 메모리 저장소로 교체할 수 있게 한다.
- 랜덤 선택은 주입 가능한 난수 공급자를 사용해 테스트 결과를 재현할 수 있게 한다.

## 4. 데이터 좌표와 수치

### 4.1 문양 좌표

- 모든 문양은 0~100 정규화 좌표를 사용한다.
- 입력 화면은 실제 좌표를 정규화한 뒤 코어에 전달한다.
- 코어는 화면 크기, 해상도와 원근을 알지 않는다.

### 4.2 마나

- 한 턴의 내부 마나 총량은 100이다.
- 이 수치는 구현과 테스트를 위한 단위이며 UI에 숫자로 노출하지 않는다.
- 마나는 획을 구성하는 선분 길이를 합산해 소비한다.
- 말소 구역 안의 선분은 1.75배 비용을 사용한다.
- 턴 종료 시 남은 마나는 이월하지 않는다.

### 4.3 판정

- 핵심점과 순서 40%
- 경로 정확도 35%
- 시작점, 종점과 교차 15%
- 마나 효율 10%
- 필수 조건 실패 시 점수와 관계없이 시전 반려

## 5. 도메인 모델

### 5.1 주문

주문은 다음 정보를 가진다.

- 식별자와 표시명
- 공격, 방어 또는 해제 카테고리
- 주문서 등급
- 요구 획수
- 기본 피해 또는 방어 효과
- 권장 마나 길이
- 문양 명세
- 일반 방어막 관통 여부
- 절대 방어막 제거 횟수

### 5.2 문양

- 정규화 좌표와 벡터
- 하나 이상의 획 명세
- 시작점, 종점과 핵심점
- 기준 경로
- 허용 반경
- 필수 교차점
- 입력 획과 마나 사용 결과
- 판정 점수, 등급과 실패 사유

### 5.3 전투원

- 현재 및 최대 HP
- 수치형 일반 방어막
- 횟수형 절대 방어막
- 생존 여부
- 플레이어의 남은 마나와 획
- 적 패턴 진행 위치와 발동한 단계 조건

### 5.4 진행 상태

- 현재 층과 장면
- 습득 주문 집합
- 완료한 전투
- 선택한 보상
- 읽은 기록
- 튜토리얼 완료 상태
- 체크포인트
- 주문별 최고 판정

## 6. 문양 판정 엔진

### 6.1 입력

- 주문 ID
- 시간순으로 정렬된 획 배열
- 획마다 하나 이상의 정규화 좌표
- 활성 말소 구역 배열
- 입력 방식(Pencil 또는 손가락)

### 6.2 처리

1. 요구 획수 검사
2. 빈 획과 입력판 범위 검사
3. 실제 선 길이와 말소 구역 가중 길이 계산
4. 획별 시작점과 종점 검사
5. 핵심점 통과 순서 검사
6. 기준 경로와 입력 샘플 사이 거리 계산
7. 필수 교차점 검사
8. 항목별 점수와 강제 실패 조건 계산
9. 최종 등급과 실패 원인 반환

### 6.3 결과

- 0~100 내부 점수
- 시전 등급
- 공격 배율
- 사용한 마나
- 말소 구역 안에서 사용한 마나
- 통과 및 누락 핵심점
- 가장 중요한 실패 원인
- 디버깅용 항목별 점수

## 8. 적 행동 엔진

### 8.1 기록 관리자

- HP 120
- 기록 찌르기 피해 14
- 문서 방벽 22
- 공격과 방벽 반복
- HP 50% 이하에서 고정 말소 구역 1개 생성

### 8.2 관측 잔류체

- HP 72
- 유리 파편 피해 10
- 초점 고정으로 강공격 예약
- 집속 파편 피해 26

### 8.3 관측 관리자

- HP 165
- 시작 절대 방어막 1회
- 파편 조사 피해 18
- 초점 고정 후 균열 조사광 피해 42
- HP 50% 이하에서 절대 방어막 1회 재생성

## 9. 진행과 보상

### 9.1 층 상태

- 10층: 잔광 말소 습득 → 균열 절단 습득 → 문 개방
- 9층: 기록 관리자 → 후보 3개 중 선택 → 방벽 관통 등록 → 문 개방
- 8층: 초급 방벽 습득 → 관측 잔류체 → 봉인 해제 습득 → 관측 관리자 → 데모 종료

### 9.2 보상

- 보상 후보는 이름 일부, 카테고리와 등급 공개 데이터를 가진다.
- 선택은 한 번만 확정할 수 있다.
- 9층의 세 후보는 데모에서 모두 방벽 관통으로 해석된다.
- 선택 직후 저장해 중복 획득을 막는다.

### 9.3 저장

- Codable 기반 버전이 있는 저장 데이터
- 원자적 파일 교체 방식
- 손상 데이터 감지 및 초기 상태 복구
- 테스트용 메모리 저장소
- 체크포인트 기준 전투 재시작

## 10. 테스트 전략

### 10.1 단위 테스트

- 각 주문의 정답 경로가 승인되는지
- 핵심점 누락과 획 초과가 반려되는지
- 우회 경로가 마나를 더 사용하는지
- 말소 구역 통과 비용이 증가하는지
- 공격 등급별 피해 배율이 적용되는지
- 일반·절대 방어막 처리 순서가 맞는지
- 2획과 연속 시전 제한이 지켜지는지
- 적 패턴이 문서 순서대로 반복되는지
- HP 50% 조건이 한 번만 발동하는지
- 보상 선택과 저장 복원이 결정적인지

### 10.2 통합 시뮬레이션

- 기록 관리자 전투를 정답 문양으로 끝까지 자동 진행
- 관측 잔류체의 강공격에 초급 방벽 적용
- 관측 관리자의 절대 방어막을 해제하고 처치
- 10층에서 8층 데모 종료까지 진행 상태 전이

### 10.3 빌드 검증

- iPadOS Simulator용 Debug 빌드
- 모든 XCTest 통과
- 문서와 코드의 콘텐츠 ID 일치 검사

## 12. 완료 정의

비UI 프로토타입은 다음 조건을 모두 만족하면 완료로 본다.

- 문서에 정의된 주문 5종이 데이터로 존재한다.
- 정규화된 획 입력으로 모든 주문을 판정할 수 있다.
- 전투 엔진이 UI 없이 세 적과 전투를 끝까지 처리한다.
- 일반 방어막, 절대 방어막, 말소 구역과 강공격이 작동한다.
- 10층에서 8층 종료까지 진행 상태를 만들고 저장·복원할 수 있다.
- 핵심 규칙을 검증하는 자동 테스트가 존재한다.
- iPadOS 프로젝트가 빌드된다.
