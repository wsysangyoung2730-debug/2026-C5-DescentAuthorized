# 실기기 카메라·표면 표현 차이 분석 (#111)

분석일: 2026-09-18

브랜치: `fix/#111-device-camera-analysis`

기준: 최신 `origin/develop`의 `7db2879b8299fabbab05c2007e477c728fd5c07a`

범위: 분석만 진행. 런타임 코드·3D 자산·조명 수치는 변경하지 않음.

## 사용자 환경과 관찰

사용자 보고 환경은 iPad Pro 13인치 M5, Xcode 직접 실행이다. 해당 기기의 iPadOS 버전, 앱 빌드 커밋, 그래픽 품질 설정, 고정 상태에서도 기울어지는지는 확인되지 않았다. 로컬 기기 목록의 다른 모델에 대한 캐시 정보를 사용자 기기의 정보로 간주하지 않았다. 이번에는 해당 실기기의 실행 중 카메라·재질 값을 확보하지 못했다.

제공된 6개 스크린샷에서는 다음 현상이 구분된다.

- 10층 도입부와 8층 보스 패배: 방 전체가 작아져 검은 공간에 기울어진 채 보인다.
- 10층·8층 조사 화면: UI는 수평인데 3D 방만 기울어지고 천장을 향한다.
- 같은 조사 화면: 벽의 표면 무늬는 남지만 바닥과 일부 기물이 강하게 하얗게 날아간다.
- 9층 보상 화면은 상대적으로 안정적인 구도와 명암을 보인다. 8층 문 앞 화면도 방 전체가 축소되는 현상은 보이지 않는다.

스크린샷은 모두 4:3이다. 화면 비율 하나로 장면 전체의 축소·기울어짐을 설명하기 어렵다. 스크린샷 자체에 밝기 차이가 기록되어 있으므로 패널 밝기나 화면 표시 설정만을 원인으로 지목하지 않는다.

## 코드·자산에서 확인한 사실

### 카메라

- `RealityStageView.swift:306`은 `.nonAR`, `automaticallyConfigureSession: false`로 ARView를 생성한다. 현재 소스 검색에서는 CoreMotion 기반 기울기 입력을 찾지 못했다. 기기 자이로가 직접 시점을 바꾼다고 볼 근거가 없다.
- 10층, 8층 잔류체 방, 8층 보스방, 9층 기본 USDC는 모두 `upAxis = Z`, `metersPerUnit = 1.0`이다. 검사한 작성 카메라의 월드 스케일은 `(1, 1, 1)`이고 초점거리/조리개 비율도 일관된다. 원본 카메라에 100배 스케일 오류가 있다고 확인된 것은 아니다.
- `RealitySceneController.swift:1530`은 가져온 카메라의 월드 행렬과 카메라 컴포넌트를 복사한다. 설치 시 새 PerspectiveCamera에 적용한다.
- 같은 파일 `:906`의 시야 회전은 월드 위쪽을 `(0, 1, 0)`으로 고정한다. 도입부 `:950`와 패배 연출 `:989`의 높이 이동도 월드 Y값을 변경한다.
- 조명 배치에서는 카메라 위치의 Y/Z 절댓값을 비교해 Y-up 여부를 추정한다(`:1826`). 카메라 조작에는 이와 같은 판단도 적용하지 않는다.
- 가져온 뒤의 실제 좌표축, 행렬 분해 후 스케일, 최종 활성 카메라 상태를 검증하는 진단 정보가 충분하지 않다.

**해석:** 원본 Z-up과 런타임 Y-up 가정 사이의 변환 계약이 명시적이지 않다. 실제 가져온 좌표계가 Z-up이면 좌우 회전이 수평 회전 대신 롤처럼 나타날 수 있다. 다만 RealityKit이 가져오기 단계에서 좌표계를 정규화할 수 있으므로, 원본 메타데이터만으로 실기기에서 축 변환이 실패했다고 확정할 수 없다. 방이 작아지는 현상은 이 축 문제만으로 확정 설명하지 못하며, 도입부·패배 연출 전후의 카메라 행렬, 스케일, 투영값, 활성 카메라를 별도로 비교해야 한다.

### 질감·조명·반사

- 검사한 10층·8층 잔류체 방의 벽/바닥은 색상, 거칠기, 노멀 맵 연결을 가진다. 색상 텍스처는 sRGB, 거칠기·노멀은 raw로 지정되어 있다. 노멀의 scale/bias도 표준 디코딩 형태다. 이 범위에서는 재질을 통째로 빠뜨렸다는 근거가 없다. 실기기의 실제 텍스처 디코딩 성공까지 확인한 것은 아니다.
- `installPortableRoomLighting`은 10층 6개, 8층 잔류체 방 4개, 보스방 6개의 추가 스포트라이트를 설치하고 입력 밝기에 `2^0.5`를 곱한다(`:1835`). 9층 직접 조명은 별도의 구성과 `2^-0.5` 계수를 쓴다. 기본 출력·개수·배치가 다르므로 총 조도가 정확히 두 배라는 의미는 아니다.
- 모든 방의 HDR 반사환경에 `intensityExponent = 2.5`를 적용한다(`:1916` 부근). Apple 문서상 이 값은 로그 스케일이다. 기본 강도와 동일한 설정이 아니다.
- 가져온 조명을 제거하는 코드는 Point/Spot/Directional 컴포넌트만 대상으로 한다. 반면 원본 USDC에는 10층 RectLight 6개+DomeLight 1개, 8층 잔류체 DiskLight 3개+DomeLight 1개, 보스방 DiskLight 4개+DomeLight 1개, 9층 RectLight 6개+DiskLight 6개+DomeLight 1개가 남아 있다. 이들이 실기기에서 실제 조명으로 활성화되는지는 미확인이다. 중복 조명은 확인해야 할 가설이지 확정 원인이 아니다.
- 앱에서 명시적으로 노출을 설정하는 코드는 검색되지 않았다. 밝은 원본 표면, 반사환경, 직접 조명, 렌더러의 최종 명암 변환을 분리해서 비교해야 한다.
- 그래픽 품질은 저/중/고에 따라 다른 USDC를 읽고 텍스처 최대 해상도 512/1024/2048, 그림자 조명 수 0/2/4로 나뉜다. 기기별 저장 설정이 다르면 선명도와 입체감도 달라질 수 있다. 현재 두 실행 환경의 실제 설정값은 확보되지 않았다.

**해석:** 사진은 단순한 텍스처 해상도 저하보다 조명·반사에 의해 표면의 색과 거칠기 차이가 사라지는 현상을 우선 의심하게 한다. 질감 복원을 위해 텍스처 해상도부터 올리면 원인 해결 없이 메모리만 늘릴 수 있다. 반대로 조명만 줄이면 된다고 확정해서도 안 된다. 실기기 재질 연결과 품질 설정을 함께 확인해야 한다.

## 시뮬레이터 검증의 한계

#110 기록은 iPad Pro 13인치 M5, iOS 26.5 시뮬레이터의 자산 미리보기 확인이다. 실제 플레이의 도입부→조사→패배 연출 전체나 물리 기기의 렌더링 일치 검증을 완료한 기록은 아니다. 같은 이름의 시뮬레이터가 실기기 렌더링 결과까지 보장한다고 해석하면 안 된다. 현재 자료로 M5 GPU 결함, 특정 iPadOS 버그, RealityKit 가져오기 차이 중 하나를 확정하지 않는다.

## 후속 확인·수정 순서

1. 같은 커밋·품질 설정·진입 경로로 비교한다. 빌드 식별값, OS, 실제 로드 자산, HDR 적용 완료 여부를 기록한다.
2. 도입부/조사/패배 전후에 가져온 루트와 카메라의 월드 행렬·축·스케일·FOV·클리핑값을 비교한다. 최종 활성 카메라가 의도한 런타임 카메라인지도 확인한다.
3. 확인된 가져오기 좌표계에 맞춰 카메라·이동·조명의 공통 축 기준을 명시하고 위치 크기로 축을 추정하는 방식을 제거한다. 무조건 90도 돌리는 보정은 피한다.
4. 같은 카메라에서 색상만 보는 기준 화면, 반사환경만 사용한 화면, 직접 조명만 사용한 화면, 결합 화면을 짧게 비교한다. 텍스처 누락/색공간/조명 중복/과도한 밝기를 분리한다.
5. 실기기 기준으로 반사환경과 직접 조명을 조정하고, 필요한 경우 가져온 조명을 명확히 비활성화한다. 해상도와 기물 개수는 원인을 확인하기 전에 늘리지 않는다.
6. 최소 검증 범위는 10층 도입부·조사, 8층 조사·보스 패배, 정상 비교용 9층 보상이다. 전체 게임 테스트나 대규모 자산 재출력은 이번 분석 범위에 포함하지 않았다.

## 실행 비교로 확정된 원인 (후속 확인)

사용자가 POS 기기를 테스트 기기로 확인했고 USB 연결 후 직접 진단했다. 실제 모델은 iPad Pro 13인치 M4, iPadOS 26.6.2이며 비교 시뮬레이터는 iPad Pro 13인치 M5, iOS 26.5다. `66f91d8`의 동일 Debug 진단, 10층 main, medium 품질을 사용했다.

- 양쪽에서 기본/0.2 rad 좌우 회전/넘어짐 세 상태의 root·authored·entity·rendered 카메라 행렬이 모두 일치했다(최대 원소 차이 0).
- 가져온 방의 최상위 스케일이 0.01이고 축은 Z-up으로 남았다. 원본 카메라 `(0, -8.2, 1.65)`가 런타임에서 `(0, -0.082, 0.0165)`가 됐다.
- Y축 좌우 회전은 이 좌표계에서 롤처럼 보인다. 월드 단위 0.72 이동은 원본 방 기준 72m에 해당하고, 의도한 수직축도 아니다. 방이 작게 멀어지는 현상을 양쪽에서 직접 재현했다.
- 12개 방/품질 USDC의 default prim은 모두 identity다. 따라서 가져오기 루트에서 미터/Z-up→미터/Y-up 계약을 적용하고, 그 이후에 카메라 스냅샷을 잡는 방식으로 수정한다. 조명은 변하지 않은 방의 로컬 좌표로 설치한다.
- 조명 강도를 바꾸지 않고 이 좌표만 수정했을 때 과도한 백색 번짐도 줄었다. 최상위 크기는 카메라뿐 아니라 실제 광원과 표면 사이의 거리에 영향을 주었다. 별도의 M4/M5 렌더러 결함이나 텍스처 누락을 이 현상의 원인으로 확인한 것은 아니다.

수정 전 수치 증거는 `diagnostics-111/before-device`와 `before-simulator`에 보관한다. 이 결과는 위의 초기 미확정 분석을 갱신한다. 이전에 정상으로 보았던 실행과의 빌드·품질·경로 차이는 확보하지 못했지만, 현재 동일 조건에서는 시뮬레이터에서도 재현된다.

10층 보정 후에도 양 플랫폼 세 상태의 네 행렬은 최대 차이 0으로 일치했다. 카메라는 `(0, 1.65, 8.2)`, 스케일 약 1이며, 좌우 회전은 위치를 유지하고 넘어짐은 높이 약 0.928m의 실내 시점으로 끝난다. 직접 조명과 HDR 강도·텍스처는 변경하지 않았다. 수정 전후 PNG도 직접 확인했다. 수치는 `diagnostics-111/after-device`, `after-simulator`에 보관한다.
