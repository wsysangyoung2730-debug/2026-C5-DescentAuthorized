## 2. 조사로 확인한 범위

| 항목 | 현재 상태 | 이번 구현 범위 |
|---|---|---|
| 7~5층 배경 | 기존 3D 로딩 및 전투·보상·문 시점 연결 | 최신 Blender의 6개 방으로 재수출·교체 |
| 4~1층 배경 | 게임 규칙과 2D 진행 화면 존재, 3D 장면 경로 없음 | 층마다 A/B/관리자 3개씩 총 12개 방 연결 |
| 7~5층 캐릭터 | 6종, 기존 5관절 리그와 모션 | 배치 갱신 및 무기·장식 변형을 개선한 모션 |
| 4~1층 캐릭터 | 제공 GLB 12종 | 리깅 준비, 배치, 개별 대기·공격·소멸 모션 |
| 전체 | 18개 방, 18종 캐릭터 | 동일한 장면 로더·품질 설정·전투 이벤트 체계 사용 |

신규 12종은 합계 약 181.88MiB, 삼각형 276,248개다. 각 파일은 메시 1개·재질 1개·8192×8192 JPEG 1장을 포함한다. 3층 관리자는 55관절 스킨이 있고, 다른 11종에는 스킨/관절이 없다. 12종 모두 애니메이션 클립은 없다. 이는 파일 구조 조사이며, 기존 55관절의 가중치 품질이나 메시 분리 가능성을 검증한 결과는 아니다.

8K 텍스처를 그대로 앱에 넣지 않는다. 기존 2048/1024/512 품질 단계로 변환하되 얼굴·손·문양 가독성을 실제 전투 시점에서 평가한다. 압축 GLB 용량과 GPU 메모리는 다른 지표로 기록한다.

근거 파일:

- `source-baseline.json`: 저장된 Blender 원본 경로·수정시각·크기·SHA-256과 Git 기준점.
- `blender-scene-inventory.json`: 현재 Blender에서 읽은 18개 장면, 카메라, 스폰 및 상호작용 이름. 현재 활성 카메라가 곧 전투 카메라라는 뜻은 아니다.
- `enemy-inventory.json`: 신규 12종의 경로·해시·삼각형·리그·텍스처 정보.

## 3. 최신 Blender 기준과 보존할 수정

현재 열린 파일은 `DA_F01_F02_F03_F04_F05_F06_F07_F08_F09_F10_Combined_v067_floor4_door_backwalls.blend`이며 조사 시 미저장 변경은 없었다. 크기는 2,801,922,769바이트다. v067이라는 이름만 보고 오래된 복사본이나 v051 통합본으로 되돌리지 않는다. 구현 시작 시 해시가 달라졌으면 사용자 최신 편집을 반영하여 기준 목록을 갱신한다.

보존 항목:

1. 각 관리자 방의 새 스테이지와 주변 소품 배치, 1·2층 잔류체 전용 받침대.
2. 1~3층 하강문·비석·발판 중앙 정렬과 가까워진 카메라, 4층 공용 하강 비석, 5층 앞으로 이동한 비석·발판·카메라.
3. 2층 전투 카메라의 확대, 3층 바닥 원위치와 가림막 이동, 1층 가로등 접지 및 문 상부 겹침 수정.
4. 1~4층 관리자 방에서 제거한 고정 보상 두루마리와 잔류체 방의 불필요한 공중 두루마리를 다시 넣지 않는다. 비석·받침대와 보상 슬롯 앵커는 유지한다.
5. 중앙문과 층 하강문은 역할과 외형을 구분한다. 기존 1층 중앙문은 승인된 형태를 유지한다.

내보내기는 원본 복제본에서 수행한다. 기존 `export_rooms.py`는 선택·재질·이미지 크기·보상 오브젝트 등을 바꾸므로 열린 원본에 그대로 실행하지 않는다. 6층 장면 등 사용자가 0인 장면도 저장 후 남도록 모든 대상 장면을 명시적으로 보존한다. 검토용 캐릭터는 `runtime_actor_preview` 등 명시적 표식으로 배경 수출에서 제외해 이중 배치를 방지한다.

- `docs/reality-assets/expansion-integration/export_rooms.py`, `repair_portable_surfaces.py`, `optimize_portable_exports.py`: 기존 파이프라인을 바탕으로 별도 최종 수출 설정을 만든다.

구현 순서:

1. 장면별 필요한 메시·카메라·앵커만 선택한다. 숨겨진 이전 단상, 검토용 캐릭터, 고정 보상 두루마리와 작업용 오브젝트는 명시적 제외 목록으로 관리한다.
2. UV·금속·거칠기·발광·투명도를 앱에서 지원하는 재질로 변환한다. 검정 대리석·황동·유리·발광이 Blender와 다르게 보이는지 대표 방에서 먼저 판단한다.
3. 단위와 좌표축, 카메라 초점거리/시프트/화면비, 부모 변환을 보존한다. 여러 부모 변환을 재적용해 배경·적이 두 번 회전하지 않게 한다.
4. 3종 화질의 USDC, 환경 HDR, 목록을 앱 번들 경로에 넣는다. 모든 방을 통째로 상주시키지 않고 현재 방을 설치하며 다음 방 하나를 미리 준비한다.
5. 적은 별도 자산으로 스폰에 설치한다. 발바닥 최저점과 실제 받침대 높이로 접지하고, 키를 일괄 고정하지 말고 관리자 장식과 카메라 구도까지 고려한다.
6. 전투·보상·문 시점 변경은 같은 방 엔티티에서 카메라를 바꾸는 기존 방식으로 처리한다. #148의 비동기 의존성 준비와 메모리 경고 해제 동작을 후반층에도 적용한다.
7. 공용 보상 두루마리는 보상 단계에만 슬롯에 생성한다. 조사용 오브젝트와 기록 보상은 진행 단계에 따라 별도로 표시한다.

## 7. 카메라 및 문

- 기본 전투 카메라는 7~5층의 명시된 iPad 카메라, 4층의 iPad MainCamera, 3~1층의 A/B/C MainCamera를 사용한다. 현재 Blender의 `scene.camera`는 상세 검토 시점일 수 있어 자동 채택하지 않는다.
- 관리자 보상/하강은 `CAM_F0n_RewardSelection`, `CAM_F0n_DescentDoor`를 우선한다. `DescentDetail`이나 과거 RewardReview 카메라를 이름 유사성으로 잘못 선택하지 않는다.
- 잔류체 A/B의 중앙문 카메라 명명은 층마다 다르므로 조사 목록에서 직접 매핑한다. 조사 카메라가 없는 방에는 필요한 시점만 작업 복제본에 추가한다.
- 손·무기·왕관이 공격 때 프레임을 벗어나지 않는지와 전투 HUD/Pencil 입력 영역을 확인한다. 보상·하강 구도를 맞추려고 전투 카메라까지 변경하지 않는다.
- #149의 연속 문짝 개방은 10~8층에만 적용되어 있다. 이번에 7~1층 문을 단순 교체하면 자동으로 작동하지 않는다.
- 각 층 수출 전에 문틀/문짝/힌지/통로를 분류한다. 단일 메시 문은 원형 외관을 유지하며 필요한 부위를 분리하고, 원형 2층 문은 형태에 맞는 개방 방식을 정한다. 5층 장식 문과 실제 하강 지점을 혼동하지 않는다.
- 문 완성은 보이는 동작 종료와 게임 진행이 연결되어야 한다. 작업 취소·즉시 재진입·승인 복원 시 열린 문을 처음부터 재생하지 않는다. 문 분리 품질이 확보되지 않으면 해당 항목을 미완료로 남긴다.

## 8. 자연스러운 모션 제작 기준

### 공통 클립과 재생 계약

- 대기: 약 3~5초 순환. 작은 호흡, 머리 시선, 손의 긴장, 보조 장치 지연 움직임. 접지한 발과 받침대는 고정한다.
- 대기 변주: 고개 확인, 손/책 정리, 밸브 압력 반응 등 1~2개. 모든 적이 같은 주기로 흔들리지 않도록 시작 위상을 분산한다.
- 등장, 예고, 일반 공격, 강공격, 특수 행동, 피격, 무력화, 소멸을 상태별로 구분한다. 자유 이동용 걷기/달리기와 전신 천 시뮬레이션은 현재 고정 전투 무대의 기본 범위에 넣지 않는다.
- 일반 1.0초/타격 0.46초, 강공격 1.3초/타격 0.62초, 무력화 1.8초는 #139의 출발값이다. 캐릭터별 동작에 맞춰 조정할 때 클립과 이벤트 메타데이터를 함께 바꾼다.
- `motion.json`의 구간, `impact`, `settledAt`과 실제 애니메이션 재생을 일치시킨다. 게임 피해 계산은 기존 규칙대로 한 번만 실행하고, 화면은 해당 결과를 타격 시점에 보여준다.
- 반복 대기→예고→공격→복귀가 자연스럽게 이어지게 한다. 리그가 없는 모델 전체를 기울이거나 상하 이동시키는 것만으로 자연스러운 관절 모션을 완료 처리하지 않는다.

### 형태별 제작 방법

1. 3층 관리자의 기존 55관절은 본 이름·기본 자세·가중치를 먼저 검사하고 재사용 가능하면 유지한다. 리그가 있다고 자동으로 품질이 확보된 것으로 간주하지 않는다.
2. 나머지 11종은 머리/척추/어깨/팔꿈치/손목/골반/필요한 다리 관절을 잡는다. 무릎·팔꿈치 주변 메시가 붙어 있으면 국소 분리/보완이 먼저다.
3. 무기·방패·책·저울·등 장식은 형태가 유지되는 전용 부품/관절로 처리한다. 손과 장비의 접점은 고정하며 무기를 피부처럼 구부리지 않는다.
4. 긴 옷·쇠사슬·후면 판은 제한된 보조 관절로 후행 움직임을 준다. 물리 시뮬레이션 비용을 기본값으로 추가하지 않는다.
5. 7~5층 기존 리그는 파일만 재수출하지 않고 무기 휨이 큰 캐릭터부터 보완한다. 얼굴 표정·손가락 정밀도는 실제 모델 구조와 화면상 크기에 맞춰 결정한다.

### 소멸과 생명주기

치명타 결과 → 피격/무력화 → 코어·장식 빛 소실 → 몸체 사라짐 → 처치 대사/보상 순서를 보장한다. 전용 소멸 머티리얼의 플랫폼 호환성과 투명 재질 비용을 먼저 평가하고, 적용이 어려운 자산은 짧은 페이드와 제한된 파티클로 같은 종료 상태를 만든다. 새 리그에서 쓰러짐 가능한 범위를 넘겨 바닥이나 장식을 관통시키지 않는다.

소멸 종료 시 메시·그림자·히트박스·효과·반복 작업을 함께 비활성화한다. 일시정지는 남은 시간을 보존하고, 재시도는 대기/기본 재질로 초기화한다. 동작 줄이기는 흔들림을 줄이고 명확한 최종 상태를 제공한다. 화면 이탈/새 조우는 이전 비동기 작업을 취소한다.

## 9. 최적화와 검증 계획

수출 단계부터 8K 원본 제외·불필요한 오브젝트 제외를 적용하고, 최종 #165에서 전체 비용을 측정해 조정한다. 구조 확인 없이 일괄 폴리곤 감소를 하지 않는다.

- 자산: 기존 high/medium/low의 2048/1024/512 텍스처 구조 유지. 현재 중·저품질은 텍스처 오버라이드이며 실제 메시 LOD가 아님을 구분한다. 메시 단순화가 필요하면 스킨 가중치/장비 외곽/문양 손실까지 검토한다.
- 배경: 재질·텍스처 중복 제거, 반복 소품의 지원 가능한 인스턴스화, 고정 메시 묶기. 카메라·인터랙션·문짝·스폰을 묶거나 삭제하지 않는다.
- 조명: 환경 HDR 및 제한된 실시간 조명으로 기존 분위기 유지. 겹친 투명면·그림자·발광 효과의 GPU 비용을 실제 장면에서 확인한다.
- 로딩: #148의 다음 방 1개 준비 원칙을 A→B→관리자→다음 층 A에 확장. 화질 변경·준비 실패·메모리 경고·빠른 연속 이동 시 정리/취소를 검증한다.
- 측정: 동일 iPad/OS/화질/저장 상태에서 냉시작·재입장·즉시 문 해제·대기 후 해제를 각 3회 이상 비교. 로드 시작→디코딩→설치→실제 첫 화면을 따로 기록한다. CPU 설치 로그를 GPU 준비 완료로 간주하지 않는다.
- 성능 목표 초안: 지원할 기준 iPad에서 지속 60fps(프레임 16.7ms)를 우선 목표로 삼고, 저성능 기기는 저품질에서 안정적인 30fps(33.3ms)를 하한 후보로 평가한다. 기기 선정과 초기 측정 후 수치·메모리 예산을 확정한다. 현재 달성 수치는 없다.
- 메모리: 18개 방을 순회/역방향 재진입하는 반복에서 최고점과 해제 후 잔류량 기록. 프리로드 캐시 개수 제한을 앱 전체 메모리 상한으로 오해하지 않는다.

확인 단계:

1. 소스/수출 정적 검사: 18개 방·18종·필수 카메라/앵커·단위·텍스처 경로·클립/마커/스킨 검사. 예상은 방 54개 품질 엔트리와 캐릭터 54개 품질 엔트리이며 실제 메시 데이터가 3배 복제된다는 뜻은 아니다.
2. 대표 방에서 처음 한 번 수출→앱 표시→대기/공격 재생을 끝낸 뒤 나머지 방에 확장한다. 같은 결함을 18개 방에 복제하지 않는다.
3. 각 층 변경 시 해당 층의 준비·전투·승리·재도전·중앙문·보상·하강을 좁게 확인한다. 모션은 전투 카메라에서 대기/타격/최종 무력화와 전 구간을 확인한다.
4. 최종 통합에서 7→1층 전 경로, A/B 재개, 하강 승인 0/1/2/3 저장 복원, 보상 중 이탈, 최종 기록/인계, 화질 변경 및 메모리 경고를 확인한다. 10~8층 공유 로더·공용 두루마리·#149 문 개방의 회귀도 포함한다.
5. 시뮬레이터 빌드·진행 검사는 실기기 렌더링 성능/Pencil 조작을 대신하지 않는다. 실기기를 사용할 수 없는 경우 코드/산출물 작업은 완료하되 해당 검증은 미실시로 인계한다.

## 10. 최종 전달물과 현재 완료선

최종 산출물은 ① 최신 배치를 포함한 통합/층별 Blender 편집본 ② 18종 리그·모션 라이브러리 ③ 앱용 품질별 방/캐릭터/공용 장치·환경·메타데이터 ④ 원본과 산출물 해시 목록 ⑤ 브랜치·커밋별 완료 내역 ⑥ 실제 측정과 미검증 항목이다. 대형 Blender/원본 GLB를 앱 번들에 넣지 않으며 기존 저장소의 대용량 자산 관리 방식에 맞춰 편집본 보관 위치를 기록한다.

이번 #150에서 완료: 원격 #149 가져오기, 별도 계획 브랜치 생성, 현재 Blender 18개 방 및 12종 신규 GLB 읽기, 해시·리그·텍스처 조사, 세부 계획 기록.

이번에 실행하지 않은 항목: Blender 수정/저장, 리깅·모션 제작, 앱 코드/리소스 교체, 빌드·성능 측정, 원격 푸시/병합. 다음 실행 단계는 #151 계약 정리 → #152 대표 방 수출 검증 → #153 리그 제작 방식 확정이다.
